# RESEARCH · 个人作品集网站

> 阶段一产物。这是一份非正式笔记，用来把「为什么做、别人怎么做的、我到底要什么」先想清楚。
> 使用者画像：走 vibe coding 路线的开发者；目的是**练手 + 未来展示**；核心板块已定：**项目作品展示 + 关于我**；技术栈交给后续阶段推荐。

---

## 一、目标

**要解决什么问题**

我现在没有一个属于自己的线上「门面」。做过的东西要么散在 GitHub 仓库里，要么只躺在本地，别人（未来的雇主、合作者、客户）想了解「我会做什么、做过什么、怎么联系我」，得自己拼凑。缺一个**一眼看明白**的地方。

**为什么值得做**

- vibe coding 这条路，别人看的是**结果**。作品集就是把结果摆到台面上的地方。
- **练手价值**：用真实项目，把前端工程化、设计、构建、部署整条链路亲手走一遍。
- **长期资产**：不是一次性作业。以后每做一个新项目就往里加一条，越攒越值钱。

**做出来是什么样（一句话愿景）**

一个**加载快、看着干净、手机上也好用**的站点：打开 3 秒内就知道「我是谁 + 我做过哪些项目 + 怎么联系我」，每个项目点进去有图有真相。

## 二、调研发现

### 市面上同类产品大致分三类

1. **平台托管型**——GitHub Pages、Vercel/Netlify 官方模板、Framer / Webflow 模板、Behance / Dribbble。
   - 优点：上手快，几乎零部署成本，模板开箱即用。
   - 缺点：**模板感重、容易和别人撞脸**；展示的是平台而不是「你」；深色定制和工程细节受限。
2. **框架手写型**——Next.js / Astro / Vite + React 的作品集站点。
   - 优点：完全可控、能顺带体现技术能力、SEO 与性能可优化到位。
   - 缺点：设计与内容都得自己扛，部署要自己配。
3. **现成作品集服务**——一堆「一键生成」的 SaaS。
   - 优点：快。
   - 缺点：被模板框死，长期扩展性差。**练手价值几乎为零**，与我们的第二个目的冲突。

### 2026 的设计趋势（可借鉴的）

- **极简 + 少即是多**：留白、清晰的层级、克制的动效，是当下的主流审美。
- **暗色模式逐渐成为默认**，而不是可选。
- **Bento grid（便当格布局）** 在个人主页上很流行，适合把「关于我 / 技能 / 项目」拼成一屏。
- **移动端优先**是底线，不再是加分项。
- 反直觉的趋势：**过度 3D / 满屏动效已经腻了**，堆特效反而显得不专业。

### 别人踩过的坑（我们要避开的）

- ❌ **首屏动效/预加载动画过重**：拖慢首屏，招聘方平均只停留 6–8 秒，来不及看清就关了。
- ❌ **项目堆太多、只有截图**：20 个平庸项目不如 5 个能打的项目；只有图没有「我做了什么、用了什么、结果如何」，等于没讲。
- ❌ **满屏技术名词**：重点被淹没，看不出价值和取舍。
- ❌ **移动端没适配**：字体太小、对比度低、横向溢出。
- ❌ **只有首页能看**：点进项目/详情是空页面或死链。
- ❌ **没有明确行动入口**：看完不知道下一步该干嘛（联系我 / 看简历 / 看 Demo）。

> 一句话总结：**别人拼的是「炫」，我要拼的是「清楚 + 快 + 能落地」。**

## 三、核心需求

1. **首屏 3 秒讲清「我是谁、我能做什么」**——姓名 + 一句话定位 + 主视觉，不要用预加载动画挡路。
2. **项目作品展示**——卡片形式呈现：封面图、标题、一句话简介、技术栈标签、GitHub / 在线 Demo 链接；可点开看单个项目的详情。
3. **关于我 / 个人简介**——头像、自我介绍、技能标签、（可选）经历时间线。
4. **联系入口随手可及**——邮箱、GitHub 等社交链接，页头和页脚都能找到。
5. **响应式 + 快**——移动端优先，图片懒加载，首屏轻量，动效克制。
6. **内容可维护**——新增/修改作品只需改一个数据文件或加一篇 Markdown，不动页面结构。

## 扩展方向调研（追加 · 2026-10-06）

> 在已上线的作品集之上，评估两个扩展方向：**博客 / 分享经验**、**多种主题**。
> 本次范围：只这两个。多语言切换、访问统计本次**不调研**（当前不需要）。
> 定位：现在没什么内容给别人看，但计划把它**长期养成真正的作品集**。

### 一、目标

**要解决什么**

站已经能"展示作品"，但只有一个作品列表。想让它**能长期长内容**（写东西攒着），并且**能换外观**。

**为什么值得做**

- 博客：2026 年出现"个人博客文艺复兴"——AI 生成内容泛滥，**真人写的、有观点的独立博客反而变稀缺**，更容易被搜索和 AI 引用。
- 主题：暗色已是主流默认，**明暗切换基本是"有没有"的问题**，不再是加分项。

**大致是什么样**

不改动现有结构，**各加一节**：一个能按时间读文章的地方；一个能切换明暗的地方。克制、不喧哗。

### 二、市场与同类产品调研

**博客：三种做法**

| 做法 | 代表 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 纯第三方平台 | Dev.to / Hashnode / Medium / Substack | 自带流量和社区 | 内容不在自己地盘，平台说了算 |
| 纯自建 | 自己的站 | 完全可控、是自己的资产 | 没人来，得自己搞流量 |
| **自建为主 + 平台同步** | 主流推荐做法 | 两边好处都要 | 多一步操作 |

- **别人怎么做**：先在自己站发，再同步到平台，并用 canonical 标记告诉搜索引擎"原文出处在自己站"，这样不丢搜索权重。（来源：misar.blog）
- **要避开**：一上来就自带评论系统 / 账号体系 / 邮件订阅——徒增维护，还容易被垃圾内容缠上。

**多种主题：其实大多数人只做"明暗"**

- 暗色使用已成主流：约 **68% 手机用户**用过暗色，有统计称 2026 年达 **78%**；Reddit 移动端 85.4%、Instagram 18–34 岁 77.2%。（来源：zipdo / gitnux 等聚合站）
- 但**"很多套主题"（海洋/森林/日落…）的样例不少，可靠的需求证据很少**——绝大多数网站只给**浅色 / 暗色 / 跟随系统**三选一。（来源：xebia、freefrontend、claritee）
- 主题切换对**可访问性**有实际好处（照顾对比度偏好）。（来源：claritee.io）

**前后端两面**

- 博客：读文章本身**不需要服务器**，靠静态内容就能支撑；只有加评论 / 统计 / 订阅时才需要外部服务（本次不调研）。
- 主题：**不需要服务器**，只要在本地记住用户选了哪套即可。
- 两个扩展都**不引入服务器**，不会破坏现在的"轻、快"基调。

**证据台账**

| 结论 | 依据 | 来源 |
| --- | --- | --- |
| 逆 AI 内容趋势，真人独立博客回潮 | 多平台同题报道 | zhuanlan.zhihu.com / cnblogs / 51cto |
| 自建 + 平台同步 + canonical 是主流做法 | 平台对比文章 | misar.blog |
| 暗色使用率约 68%–78% | 聚合统计数据 | zipdo / gitnux |
| 多数站点只做明暗，不做多套主题 | 主题实现文章与样例 | xebia / freefrontend |
| 博客有助于展示 / 求职 | 2026 多篇招聘指南 | getcraftly / saranzafar |

### 三、用户喜好与目标用户

- **谁看**：未来的雇主 / 合作者，以及任何想了解你的人。他们**看得很快**，不会为读长文停留。
- **读者偏好**：真实、有观点、有具体经验的内容，胜过泛泛的"教程搬运"。
- **写作最大的敌人是坚持**：一手吐槽集中在**内容枯竭、流量停滞、写作耗时（配图 / 排版）、自我怀疑**。（来源：知乎「长期运营个人博客的挑战」、CSDN 创作倦怠文）
- → 启示：**让"写一篇"尽可能省事**，比任何花哨功能都重要。

### 四、结论与取舍

1. **博客：值得做，但要认清它是"内容项目"不是"功能项目"。** 技术上很快能搭好；真正的风险是**写不下去**。先问自己能不能接受"偶尔一篇、可能没人看"。
2. **主题：只做"浅色 / 暗色 / 跟随系统"三选一就够**；再多的主题（海洋 / 森林…）**收益低、维护高，建议不做**。
3. **博客采用"自建为主 + 平台同步 + canonical 指回原站"**，两头好处都拿。
4. **两个扩展都是"加一节"**，不用重做现有站点，也不引入服务器，保持现在的轻快。
5. **别急着开写**：先把博客的位置留好、结构搭对；等真有内容再发第一篇，避免"空列表"的尴尬。

### 五、不确定项

- **多主题的需求证据薄弱**：只找到实现样例，没找到可靠的"用户想要多套主题"数据 → 结论属**推测**。
- 暗色使用率的**具体百分比来自聚合站**（zipdo / gitnux），非一手统计，数字可能有出入；但"暗色已主流"这个方向可信。
- "博客有助求职"多来自 2026 的**招聘指南类文章**（二手），方向可信，缺硬数据。
